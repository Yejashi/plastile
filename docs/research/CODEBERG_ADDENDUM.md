## 3. What changed since the pins

### Fluid Tile (P06 -> P06c)

### Krohnkite continuation (P02 -> P02c)

Diff sizes between the pin and the head (measured with `diff`, lines added/removed): `kwindriver.ts` +990/-689, `engine.ts` +779/-172, `control.ts` +320/-260, `kwinwindow.ts` +281/-69, `kwinsurface.ts` +280/-42, `kwinsettimeout.ts` +39/-2, `main.qml` +44/-3. Substantively (observed source unless stated):

1. **Teardown and reload are now explicit.** A new `KWinRuntime` class (`kwinruntime.ts`) owns a replaceable `KWinDriver`, with `start()`, `reloadIfChanged()` (compares a fresh `KWinConfig` with the active one, stops the driver, starts a new one, and rolls back to the previous config if the new driver throws) and `dispose()`. `res/main.qml` now keeps `property var runtime`, calls `runtime.dispose()` from `Component.onDestruction`, and reloads through a 100 ms single-shot `configReloadTimer` restarted from `Options.onConfigChanged`. `KWinDriver.dispose()` disconnects every recorded signal connection (`_connections`), disposes each `DriverWindow`, clears relocation state, window maps, shortcuts, the drag preview and D-Bus. `DriverWindow.dispose()` restores only the properties this instance managed (`noBorder`, `keepAbove`/`keepBelow`, `minimized`), with original values snapshotted on first write. Upstream commits: `8375e7b91dbd` "refactor: make driver resources disposable", `c7a9ba3ef79a` "feat: add transactional runtime reloads" (2026-09-07, measured).
2. **Timer pool gains a disposal path and a generation counter.** `KWinTimerPool` tracks `activeTimers`, and `dispose()` stops, disconnects and destroys every active and pooled QML `Timer`; a callback that fires after a `dispose()` no longer returns its timer to the pool because `generation` changed. `KWinDriver.setTimeout` wraps callbacks in `_runProtected`, which is a no-op once `_disposed` is set.
3. **README reload warning replaced.** The pinned README said configuration changes require a reboot and that toggling the script "will start multiple instances". The head README instead documents `qdbus6 org.kde.KWin /KWin org.kde.KWin.reconfigure` after `Apply`, and `kwriteconfig6 ... krohnkiteEnabled true|false` plus `reconfigure` to enable/disable. The old reload hazard is therefore acknowledged upstream as fixed by the code in item 1. This is an upstream claim backed by the code path above, not a runtime result reproduced here (inference).
4. **Re-entrancy guard changed from driver-wide to per-connection.** The pin had one `entered` boolean on the driver, so any event arriving while a handler ran was dropped. The head's `_connect()` creates one `ReentrancyGuard` per signal connection; only the same callback is blocked from re-entering itself, and the wrapper self-disconnects when `_disposed` or when `workspace` becomes undefined. Upstream commit `63780d4392d3` "REFACTOR: use per-callback re-entrancy guards" (2026-10-17, measured).
5. **Arrange is non-re-entrant with coalesced passes and explicit batching.** `TilingEngine.arrange()` now sets `_arranging`; nested requests set `_arrangePending` and are run as another pass of the same call, bounded by `MAX_ARRANGE_PASSES = 10` with a warning if it does not settle. `beginArrangeBatch()`/`endArrangeBatch()` defer arranges across multi-step actions (virtual-desktop moves, batched initial window arrangement). Upstream commits `6150c2b20399` "perf: batch initial window arrangement" and `14b557e42c8b` "PERF: batch arranges for VDesktop move shortcuts" (measured).
6. **Output-transfer completion is signal-driven with one bounded fallback timer.** The pin polled every 20 ms up to 100 ms after `sendClientToScreen` (`interval = 20`, `maxWait = 100`, see [P02-driver](SOURCE_INDEX.md#p02-driver)). At head, no 20 ms polling remains in `src/` (measured by grep for `maxWait`, `const poll`, `interval = 20`). Instead the driver marks `window.isSendingToOutput = true`, the per-window `outputChanged` handler clears the flag and advances the relocation process, and a single `setTimeout(forcedArrangeScreen, TilingEngine.SENDING_WINDOWS_MAX_WAIT_TIME)` with `SENDING_WINDOWS_MAX_WAIT_TIME = 100` forces an arrange if the signal never arrives.
7. **Geometry write path is unchanged in kind.** `DriverWindow.commit()` still ends in a single `this.window.frameGeometry = toQRect(geometry)` after `adjustGeometry()` and optional protrusion clamping. Changes: it now takes the driver context and resolves the output through `resolvedOutput`, which falls back to the active screen when the window references an already-destroyed output (a hotplug/resume crash guard, per the inline comment); it returns early on `window.deleted` and on `window.resize`, but no longer on `window.move` (the pin skipped commits during an interactive move; the head handles dragging through a separate `isDragging` path, observed in commit messages `ca2cf8a7cfd4`, not traced further). `enforceSize()` still re-commits via a 10 ms deferred `ctx.setTimeout` when the observed geometry differs from the desired one.
8. **Other growth not analyzed here.** Dock widgets dragging, shortcut sequences with register mode, directional-focus candidate fixes, min-size handling in layouts, a Cascade layout, and a `UniqueLifoFifo` utility. These do not bear on the three questions below.

## 4. Do research conclusions change?

**Scheduling model: the critique of P02 no longer describes the Codeberg head; the Plastile conclusion stands.** [STATE_OF_THE_ART.md section 4](STATE_OF_THE_ART.md#4-p02-anametologins-krohnkite-continuation) attributes to P02 a "coarse `entered` guard" and "20 ms timer steps with bounded waits". Both statements remain true of the pinned snapshot and are now false of P02c (observed source, items 4 and 6). The head moved toward what the research recommended for Plastile ("signal-driven transfers" and "deterministic unload/reload"). It still uses a fixed 100 ms fallback timer, a 10 ms `enforceSize` re-apply, a 100 ms QML reload debounce, and up to 10 synchronous full re-arrange passes per event; none of these has been measured, and the pass bound is a safety net, not a scheduling model. Plastile's decision to reconcile on a generation-checked, event-driven path without fixed settle timers is unchanged (inference). The P02c re-arrange loop is a useful comparison baseline for the M0/M1 counters: Plastile should record arrange passes per event and should not need a "did not settle" warning in ordinary operation.

**Geometry write path: unchanged.** Both P02 and P02c write `frameGeometry` once per commit from a layout-derived rectangle with constraint adjustment and an optional protrusion clamp; there is no separate commanded-versus-committed bookkeeping of the kind P07 has, and `enforceSize` still fights late application geometry through a 10 ms timer (observed source). The research's recommendation to keep desired, last-requested and observed geometry separate and to bound convergence is unchanged. One new upstream fact is worth carrying into Plastile's hotplug tests: a tiled window can transiently reference a destroyed `Output` wrapper, and passing it to `clientArea()`/neighbor lookups is described upstream as crashing KWin (observed source, comment in `kwinwindow.ts`; not reproduced).

**Teardown: the P02 weakness is addressed upstream; the Plastile gate stays.** The reload/duplicate-instance warning that STATE_OF_THE_ART cited as making reload correctness "a mandatory Plastile release gate" has been removed upstream along with a concrete disposal design: recorded signal connections, per-window property restoration, timer-pool generation invalidation, `Component.onDestruction` disposal, and rollback on failed reload (observed source). Plastile's T-series teardown requirements are not weakened by this; they are corroborated, and P02c is now a second reference implementation (after Bismuth/Karousel) of connection bookkeeping. Whether the upstream path is leak-free under rapid toggling is unknown; it has not been run here (unperformed check).

**Fluid Tile:** no conclusion changes. The project is archived; the native-tile automation analysis stands as a description of a finished codebase.
